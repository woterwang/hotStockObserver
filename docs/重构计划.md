# 重构计划（草案，待确认）

> 原则：**渐进式重构、每阶段可独立上线、先建基线再改代码、行为变化必须显式标注**。
> 不做一次性重写；每个阶段结束都要求 `npm run build` 通过 + 基线比对通过。

---

## 阶段总览

| 阶段 | 主题 | 是否改变业务输出 | 风险 |
|---|---|---|---|
| P0 | 准备：分支、测试框架、基线快照 | 否 | 低 |
| P1 | 清理与安全加固 | 否（安全相关除外） | 低 |
| P2 | 基础设施抽取：数据网关、配置、公共评分器 | 否（严格等价） | 中 |
| P3 | 策略插件化 + 数据模型统一 | 可选（见决策点） | 高 |
| P4 | 统一回测引擎 + 收益跟踪 | 是（回测口径更严格） | 中 |
| P5 | 任务治理：任务记录、幂等补跑、进程拆分 | 否 | 中 |
| P6 | 前端统一：共享类型、API 层、策略页模板 | 否 | 低 |

## P3 策略插件化 + 数据模型统一

### 3.1 策略插件
```ts
interface Strategy {
  type: StrategyType;                 // volume_surge | breakthrough | concept_resonance | hundred_day_high
  scan(date): Promise<Candidate[]>;   // T 日收盘后候选
  score(c, ctx): ScoreBreakdown;      // 组合公共评分器
  toSignal(c, opening, ctx): Signal;  // T+1 竞价后信号
}
```
- [ ] 四个策略迁移为插件；`application/` 层提供 `scanStrategy`、`generateSignals`、`backfill` 通用用例
- [ ] 突破三天（TradingSignal）作为 `breakthrough` 策略的信号阶段实现

### 3.2 数据模型（见决策点 D4）
- [ ] 新集合 `candidates`、`signals`：`strategyType`、`date`、`stockCode`、`scoreBreakdown`、`configVersion`、`riskLevel/riskTags`、`opening`、`decision`、`tracking`
- [ ] 迁移脚本：旧 6 张表 → 新 2 张表，日期统一为 `YYYYMMDD` 字符串；可回滚
- [ ] 过渡期双写 + 旧 API 保持兼容（路由内部改读新表），前端无感
- [ ] 稳定 2 周后下线旧表

**验收**：迁移前后记录数、关键字段抽样一致；所有旧 API 返回结构不变。

## P4 统一回测引擎 + 收益跟踪

- [ ] `domain/backtest/engine.ts`：按交易日逐日撮合，统一输入（signals + 配置）
- [ ] 交易成本：佣金（默认万 2.5，最低 5 元）、印花税（卖出 0.05%）、滑点（可配）
- [ ] 成交约束：一字涨停不可买、跌停不可卖（顺延）、停牌跳过
- [ ] 退出模块化：固定止损/止盈、最长持有、情绪恐慌离场、**分批止盈、移动止损**、连败减仓（落实《改进建议与优化方向.txt》）
- [ ] 指标统一：胜率、盈亏比、平均收益、最大回撤、夏普、连胜连亏、按评分/情绪/退出原因/月份分组
- [ ] 参数扫描 + 样本内/样本外切分
- [ ] 结果统一落盘 `backtest_cache/`（兼容现有分析页格式）
- [ ] 实现 `updateProfitTracking`：信号 T+1~T+N 收益、最高/最低、是否触发止损止盈，写入 `signals.tracking`
- [ ] 旧 5 套回测改为调用引擎；对比 P0 回测基线（关闭成本与约束时应一致）
